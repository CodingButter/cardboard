---
title: Writing your first pack
description: Build a new pack from scratch, load it in the runner, and iterate.
---

This guide walks through assembling a working pack from
nothing. By the end you'll have a directory that builds into a
loadable `.apg` and shows up in the game when you point the
runner at it.

The pack is intentionally minimal: it scatters a custom pickup
prefab around an existing scene. The point is not what the
pack does — it's seeing the build + load loop end-to-end.

## 1. Make a new pack directory

Packs live under `packages/`. Any subdirectory of `packages/`
with a `manifest.json` is treated as a pack by `bun run
build-packs`. Create one:

```sh
mkdir -p packages/my-pack/scripts
cd packages/my-pack
```

The final directory tree for this tutorial:

```
packages/my-pack/
├── manifest.json
└── scripts/
    └── pickups.js
```

That's it. `scenes/` and `images/` are optional in v1 — your
pack can borrow the default pack's scene by depending on it,
which is what we'll do here.

## 2. Write the manifest

Create `packages/my-pack/manifest.json`:

```jsonc
{
  "name": "my-pack",
  "version": "0.1.0",
  "engine": "two_5_d@0.1",
  "requires": [{ "id": "default", "version": "^0.2.0" }],
  "startScene": "scenes/scene1.json",
  "scripts": [
    "scripts/pickups.js"
  ],
  "items": {
    "health_potion": {
      "name": "Health Potion",
      "image": "images/items/ammo_pack.png",
      "type": "consumable",
      "stackMax": 5
    }
  }
}
```

The fields:

| Field | Required | What |
|---|---|---|
| `name` | yes | Unique pack id. Used by `requires[]` resolution. |
| `version` | yes | Semver. Used by `requires[]` range matching. |
| `engine` | yes | Engine compatibility tag. `two_5_d@0.1` for now. |
| `requires` | no | Packs this depends on. Today this is mostly aspirational — see [PACK_CHAIN](#extending-vs-replacing) below. |
| `startScene` | no | Scene path relative to the pack root. Omit to let a dependent pack supply it. |
| `scripts` | yes | ES modules to load. Run in order; each receives `ModAPI`. |
| `items` | no | Item definitions. Referenced by item id from inventories, pickups, weapon ammo refs. |
| `defaultInventory` | no | What the player spawns with. See default-pack manifest. |
| `config` | no | Path to a JSON file that deep-merges over the engine baseline. |

The reference for every field is `PackManifest` in
`packages/engine/src/AssetPack/`. The default pack's
`manifest.json` is the most complete real example.

> **Note on item images.** This tutorial points the
> `health_potion` image at `images/items/ammo_pack.png` —
> reusing the default-pack texture so we don't have to ship
> art. Pack-chain image overrides aren't fully wired yet
> (`docs/plans/PACK_CHAIN.md`), so the practical fallback is
> to copy the icon you want into your own pack's `images/`
> folder and reference it locally. For the rest of the
> tutorial the ammo-pack icon stands in fine.

## 3. Write your first script

Create `packages/my-pack/scripts/pickups.js`:

```js
/**
 * my-pack — scatter health potions across the world.
 */
export default (api) => {
  const C = api.components;

  // Register a "potion" prefab so other scripts (or a scene
  // entity placement) can call api.spawn("potion", x, y).
  api.registerPrefab("potion", (x, y) => {
    const e = api.world.spawn();
    api.world
      .add(e, C.Position, new api.Vec2(x, y))
      .add(e, C.Sprite, {
        imageId: "ammo_pack",   // borrowed default-pack sprite id
        worldHeight: 0.35,
        yOffset: 0.25,
      })
      .add(e, C.Pickup, {
        itemId: "health_potion",
        count: 1,
      })
      .add(e, C.MinimapMarker, {
        color: "#66ff88",
        radius: 0.12,
        drawForwardRay: false,
      });
    return e;
  });

  // After the scene has spawned (so the player exists), scatter
  // 5 potions at random open cells away from spawn.
  api.onWorldReady((api) => {
    const player = api.world.first(C.PlayerInput, C.Position);
    const playerPos = player ? C.Position.getOrThrow(player) : null;
    const scene = api.scene;

    let placed = 0;
    let tries = 0;
    while (placed < 5 && tries < 500) {
      tries++;
      const x = 1 + Math.floor(Math.random() * (scene.size.x - 2));
      const y = 1 + Math.floor(Math.random() * (scene.size.y - 2));
      if (scene.isWall(x, y)) continue;
      if (playerPos) {
        const dx = x + 0.5 - playerPos.x;
        const dy = y + 0.5 - playerPos.y;
        if (dx * dx + dy * dy < 9) continue; // keep clear of spawn
      }
      api.spawn("potion", x + 0.5, y + 0.5);
      placed++;
    }
    console.log(`[my-pack] scattered ${placed} potions`);
  });
};
```

This is the whole script: register a prefab, wait for the
world, scatter five of them. The pickup behaviour comes for
free because the default pack's `pickup.js` system handles any
entity with a `Pickup` component.

## 4. Build the `.apg`

From the repo root:

```sh
bun run build-packs
```

`build-packs` walks `packages/`, finds every subdirectory with a
`manifest.json`, bakes lightmaps for each scene, and zips
everything into `apps/game/public/packs/<name>.apg`. You should
see your pack in the output:

```
Building 2 pack(s) from packages/
  default → apps/game/public/packs/default.apg
  my-pack → apps/game/public/packs/my-pack.apg
```

## 5. Load your pack in the runner

```sh
bun run dev
```

Open the runner with your pack:

```
http://localhost:3000/?pack=/packs/my-pack.apg
```

The `?pack=` query takes a URL — relative paths resolve against
the runner origin, absolute URLs work for hosted packs. The
runner downloads the `.apg`, parses the manifest, loads each
script in order, calls each one with the `ModAPI`, and then
spawns the scene's initial entities.

You should see the default pack's world (we depended on it),
plus five green-marker potions scattered around — and walking
over one logs the pickup. Check the dev tools console for
`[my-pack] scattered 5 potions`.

## 6. Iterating

The dev server hot-reloads the **engine** TypeScript and the
**runner** UI — edit those and you get module reloads with
world state preserved across the boundary. Pack content goes
through a different path because it's loaded from a zip.

To iterate on a script:

```sh
# edit packages/my-pack/scripts/pickups.js
bun run build-packs
# reload the browser tab
```

Two seconds in the rebuild, one in the reload. The engine
fetches the new `.apg`, runs your new script, and you see the
change.

Things that need a rebuild:

- Pack scripts (`scripts/*.js`).
- Pack scenes (`scenes/*.json`) — and these also re-bake
  lightmaps, so they take a couple seconds.
- Manifest edits (new items, scripts, requires, etc.).
- Images, textures, item icons.

Things that don't need a rebuild:

- Engine source (`packages/engine/src/**`) — hot-reloads via
  Bun's HMR.
- The game runner UI shell (`apps/game/**`).
- The docs site (`apps/docs/**`) — separate dev server.

## Extending vs replacing

This tutorial pack **extends** the default pack. The
`requires` array in the manifest declares the dependency; the
runner currently loads the default pack first and then layers
yours on top, so all the default-pack scripts (player input,
pickup system, gun, hotbar) run before yours and the resulting
ECS world has both packs' contributions in it.

If you want to ship a **standalone** game — your own player,
your own input, your own everything — drop the `requires`
array, copy or substitute the default pack's scripts under your
own pack, and provide your own scene. The engine doesn't care;
it'll happily run a pack that doesn't depend on `default`.

The pack-chain spec — multi-pack dependency resolution, override
semantics, the community store — is designed in
`docs/plans/PACK_CHAIN.md` but only partially implemented. For
now: a single pack works fully, a pack with a single
`requires[]` entry works for the layered case the default pack
expects, and deeper chains aren't yet guaranteed to behave.
