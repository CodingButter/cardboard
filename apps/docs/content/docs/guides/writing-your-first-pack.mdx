---
title: Writing your first pack
description: Build a new pack from scratch, load it in the runner, and iterate.
---

This guide walks through assembling a working pack from
nothing. By the end you'll have a directory that builds into a
loadable `.apg` and shows up in the game when you point the
runner at it.

The pack is intentionally minimal: it scatters a custom pickup
around an existing scene. The point is not what the pack does
— it's seeing the build + load loop end-to-end.

## 1. Make a new pack directory

Packs live under `packages/`. Any subdirectory of `packages/`
with a `manifest.json` is treated as a pack by `bun run
build-packs`. Create one:

```sh
mkdir -p packages/my-pack/scripts
cd packages/my-pack
```

The final directory tree for this tutorial:

```
packages/my-pack/
├── manifest.json
├── world.json
└── scripts/
    └── pickups.js
```

`manifest.json` declares the pack's identity + content
registries. `world.json` declares the ordered script list (and,
in larger packs, persistent world entities + singletons).
`scenes/` and `images/` are optional in v1 — your pack can
borrow the default pack's scene by depending on it, which is
what we'll do here.

## 2. Write the manifest

Create `packages/my-pack/manifest.json`:

```jsonc
{
  "name": "my-pack",
  "version": "0.1.0",
  "engine": "two_5_d@0.1",
  "scope": ["game"],
  "requires": [{ "id": "default", "version": "^0.2.0" }]
}
```

The fields:

| Field | Required | What |
|---|---|---|
| `name` | yes | Pack name. With `requires[]` resolution, `id` (optional) is the globally unique handle; `name` is the human label. |
| `version` | yes | Semver. Used by `requires[]` range matching. |
| `engine` | no | Engine compatibility tag (semver). `two_5_d@0.1` for current builds. |
| `scope` | no | `["game"]` (default), `["editor"]`, or both. Game scope ships runtime content; editor scope ships panel specs / inspectors. |
| `requires` | no | Packs this depends on. Override semantics + resolver are designed in [PACK_CHAIN](#extending-vs-replacing) below. |
| `startScene` | no | Scene path relative to the pack root. Omit when extending another pack that supplies the start scene. |
| `config` | no | Path to a JSON file that deep-merges over the engine baseline. |
| `tileTextures` / `tilePresets` / `tileSheets` | no | Tile art. Game-scope packs that ship walls/floors set these. |
| `sprites` | no | Sprite catalog keyed by id (referenced by `Sprite.imageId`). |
| `audio` | no | Sound registry keyed by id (referenced by `api.audio.play`). |
| `components` | no | Manifest-declared component types (`name`, optional `schema`, optional `tags`). Registered before scripts run. |
| `prefabs` | no | Editor-authored declarative prefabs keyed by id. |
| `editorPanels` | no | (Editor scope only) JSON panel-spec files contributed to the editor's docks. |

The reference for every field is `PackManifest` in
`packages/engine/src/AssetPack/types.ts`. The default pack's
`manifest.json` is the most complete real example.

> **Notes on the new shape.**
>
> - The ordered list of scripts to run is **not** a manifest
>   field. It lives in `world.json.scripts[]`. See step 3.
> - Item definitions and the player's starting inventory are
>   **not** manifest fields. Items are entities carrying
>   `Item` + `Stackable` (+ optional `Equippable` / `Weapon`)
>   components; the starting inventory is declared on the
>   persistent player entity in `world.json`. For a working
>   pattern, read `packages/default-pack/scripts/setup/load-items.js`
>   and `packages/default-pack/world.json`.

## 2b. Write the world file

Create `packages/my-pack/world.json`. The minimum is the script
list:

```jsonc
{
  "scripts": [
    "scripts/pickups.js"
  ]
}
```

The pack-builder also walks `Scripts.refs[]` on world-scope
entities and on scene controllers, so larger packs split their
scripts across `world.json.scripts[]` + entity-attached refs.

## 3. Write your first script

Create `packages/my-pack/scripts/pickups.js`:

```js
/**
 * my-pack — scatter extra ammo packs across the world.
 *
 * Reuses the default pack's `rifle_ammo` item id (registered by
 * `packages/default-pack/scripts/setup/load-items.js` into the
 * `ItemRegistry` singleton). When you're ready to ship your own
 * item, declare it in your pack's `data/items.json` and load it
 * into the same registry from a `setup/` script — see the
 * default pack for the working pattern.
 */
export default (api) => {
  const C = api.components;

  // Local helper: spawn one pickup at (x, y).
  // (Prefabs are an editor-only declarative asset and don't
  // exist as a runtime ModAPI concept — pack scripts build
  // entities directly via api.world.spawn() + api.world.add().)
  function spawnPickup(x, y) {
    const e = api.world.spawn();
    api.world
      .add(e, C.Position, new api.Vec2(x, y))
      .add(e, C.Sprite, {
        imageId: "ammo_pack",   // borrowed default-pack sprite id
        worldHeight: 0.35,
        yOffset: 0.25,
      })
      .add(e, C.Pickup, {
        itemId: "rifle_ammo",   // default-pack-registered item id
        count: 30,
      })
      .add(e, C.MinimapMarker, {
        color: "#66ff88",
        radius: 0.12,
        drawForwardRay: false,
      });
    return e;
  }

  // After the scene has spawned (so the player exists), scatter
  // 5 pickups at random open cells away from spawn.
  api.onWorldReady((api) => {
    const player = api.world.first(C.PlayerInput, C.Position);
    const playerPos = player ? C.Position.getOrThrow(player) : null;
    const scene = api.scene;

    let placed = 0;
    let tries = 0;
    while (placed < 5 && tries < 500) {
      tries++;
      const x = 1 + Math.floor(Math.random() * (scene.size.x - 2));
      const y = 1 + Math.floor(Math.random() * (scene.size.y - 2));
      if (scene.isWall(x, y)) continue;
      if (playerPos) {
        const dx = x + 0.5 - playerPos.x;
        const dy = y + 0.5 - playerPos.y;
        if (dx * dx + dy * dy < 9) continue; // keep clear of spawn
      }
      spawnPickup(x + 0.5, y + 0.5);
      placed++;
    }
    console.log(`[my-pack] scattered ${placed} pickups`);
  });
};
```

This is the whole script: define a local spawn helper, wait
for the world, scatter five pickups. The pickup behaviour
comes for free because the default pack's pickup system handles
any entity with a `Pickup` component.

## 4. Build the `.apg`

From the repo root:

```sh
bun run build-packs
```

`build-packs` walks `packages/`, finds every subdirectory with a
`manifest.json`, bakes lightmaps for each scene, and zips
everything into `apps/game/public/packs/<name>.apg`. You should
see your pack in the output:

```
Building 2 pack(s) from packages/
  default → apps/game/public/packs/default.apg
  my-pack → apps/game/public/packs/my-pack.apg
```

## 5. Load your pack in the runner

```sh
bun run dev
```

Open the runner with your pack:

```
http://localhost:3000/?pack=/packs/my-pack.apg
```

The `?pack=` query takes a URL — relative paths resolve against
the runner origin, absolute URLs work for hosted packs. The
runner downloads the `.apg`, parses the manifest, walks
`world.json.scripts[]` (plus any entity-attached
`Scripts.refs[]`), loads each script in order, calls each one
with the `ModAPI`, and then spawns the scene's initial
entities.

You should see the default pack's world (we depended on it),
plus five extra green-marker ammo pickups scattered around —
and walking over one adds 30 rounds to your rifle ammo. Check
the dev tools console for `[my-pack] scattered 5 pickups`.

## 6. Iterating

The dev server hot-reloads the **engine** TypeScript and the
**runner** UI — edit those and you get module reloads with
world state preserved across the boundary. Pack content goes
through a different path because it's loaded from a zip.

To iterate on a script:

```sh
# edit packages/my-pack/scripts/pickups.js
bun run build-packs
# reload the browser tab
```

Two seconds in the rebuild, one in the reload. The engine
fetches the new `.apg`, runs your new script, and you see the
change.

Things that need a rebuild:

- Pack scripts (`scripts/*.js`).
- Pack scenes (`scenes/*.json`) — and these also re-bake
  lightmaps, so they take a couple seconds.
- Manifest edits (new components, sprites, requires, etc.).
- `world.json` edits (new scripts, persistent entities,
  singletons).
- Images, textures, item icons.

Things that don't need a rebuild:

- Engine source (`packages/engine/src/**`) — hot-reloads via
  Bun's HMR.
- The game runner UI shell (`apps/game/**`).
- The docs site (`apps/docs/**`) — separate dev server.

## Extending vs replacing

This tutorial pack **extends** the default pack. The
`requires` array in the manifest declares the dependency; the
runner currently loads the default pack first and then layers
yours on top, so all the default-pack scripts (player input,
pickup system, gun, hotbar) run before yours and the resulting
ECS world has both packs' contributions in it.

If you want to ship a **standalone** game — your own player,
your own input, your own everything — drop the `requires`
array, copy or substitute the default pack's scripts under your
own pack, and provide your own scene. The engine doesn't care;
it'll happily run a pack that doesn't depend on `default`.

The pack-chain spec — multi-pack dependency resolution, override
semantics, the community store — is designed in
`docs/plans/PACK_CHAIN.md` but only partially implemented. For
now: a single pack works fully, a pack with a single
`requires[]` entry works for the layered case the default pack
expects, and deeper chains aren't yet guaranteed to behave.
