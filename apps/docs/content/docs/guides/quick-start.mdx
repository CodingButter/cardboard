---
title: Quick start
description: Clone, install, run, and edit a pack script in ten minutes.
---

This guide takes you from a fresh checkout to seeing your own
edit reflected in the browser. The whole loop is under ten
minutes on a warm machine.

## Prerequisites

You need [Bun](https://bun.sh) installed. cardboard is
Bun-first — every script in the repo assumes `bun` is on your
`$PATH`. macOS / Linux / WSL all work.

```sh
curl -fsSL https://bun.sh/install | bash
bun --version
```

That's the only required dependency. The engine, runner, and
docs site all build from source with no system toolchain beyond
Bun itself.

## Clone and install

```sh
git clone https://github.com/CodingButter/cardboard.git
cd cardboard
bun install
```

`bun install` resolves the workspace graph automatically. The
root `package.json` declares `workspaces: ["packages/*", "apps/*"]`,
so every package — engine, default pack, docs site, game
runner, pack builder — links into the same `node_modules`
tree.

## Build the default pack

The game runs against `.apg` asset packs. Build the default pack
once so the runner has something to load:

```sh
bun run build-packs
```

This walks every `packages/*-pack/` directory, bakes lightmaps,
zips the contents into an `.apg`, and writes the result to
`apps/game/public/packs/default.apg`. The default pack is the
only one that ships in the repo today.

## Run the dev server

```sh
bun run dev
```

Opens the game on `http://localhost:3000`. You should see:

- A first-person view inside a room.
- An assault rifle viewmodel pinned to the bottom of the screen.
- A minimap top-left, with your position and facing.
- A reticle in the centre.
- An inventory hotbar across the bottom-centre. Slot 1 holds
  the rifle.
- Yellow ammo-pack pickups scattered around the open cells.

Click the canvas to capture the mouse. WASD walks, mouse
turns, scroll cycles hotbar, left-click fires, R reloads,
Ctrl+\` toggles a stats overlay.

## Edit one script

Everything you see — the player, the gun, the pickups, the
hotbar, the minimap — is implemented in pack scripts, not in
the engine. The engine ships zero gameplay code.

Open `packages/default-pack/scripts/hello.js` and find this
line near the bottom of the ammo-scatter block:

```js
if (rand() < 1 / 25) {
  ammo(x + 0.5, y + 0.5);
  count++;
}
```

That `1 / 25` means "1 in 25 open cells gets an ammo pack."
Change it to `1 / 5`:

```js
if (rand() < 1 / 5) {
  ammo(x + 0.5, y + 0.5);
  count++;
}
```

Save the file. The dev server already hot-reloads engine code,
but **pack content needs a rebuild** because the runtime loads
it from the `.apg` zip, not from disk:

```sh
bun run build-packs
```

Reload the browser tab. The world is now five times as littered
with ammo packs. Open the dev tools console and you'll see the
new count logged by `hello.js`:

```
[mod] scattered 234 ammo packs
```

## What just happened

You changed a pack script. `bun run build-packs` re-zipped the
default pack into `apps/game/public/packs/default.apg`. On
reload, the runner fetched the new `.apg`, extracted the
manifest, walked `world.json.scripts[]` (plus any
entity-attached `Scripts.refs[]`), loaded each script as an ES
module, and called the default export with the live `ModAPI`
instance. `hello.js` ran, registered its system + its
ammo-scatter, and the engine carried on.

That's the whole loop. The engine doesn't know what an "ammo
pack" is. It only knows how to spawn entities with components
and run systems against them; the pack tells it what those
components and systems are.
