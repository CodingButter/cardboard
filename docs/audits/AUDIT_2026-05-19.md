# Audit 2026-05-19 — Docs reorg execution record

This audit-of-record captures the reorg of `docs/` performed on
2026-05-19. It's the snapshot to consult when reasoning about the
*current* docs/ layout; the prior 2026-05-16 audit (since deleted)
produced the inventory + Option A vs Option B plan that this reorg
implements.

---

## What the audit found

The 2026-05-16 plan-doc audit (18 docs, 767 lines) surfaced three
structural problems in the docs/ tree:

1. **Top-level docs/ was a flat dumping ground.** Plan-of-record
   docs (`PLAN.md`, `SESSION_STATE.md`, `IDEAS.md`) sat next to
   process docs (`PAGE_BUILD_PROCESS.md`,
   `EDITOR_DESIGN_INVENTORY.md`) and next to standalone audit
   reports (the 2026-05-16 plan-doc audit, the editor dock-library
   evaluation, the editor UI audit — all since deleted). No visual
   / structural cue separated them, and the count had grown to the
   point where the directory listing no longer told you what kind
   of doc each entry was.
2. **The lights-as-entities refactor doc and
   `docs/plans/LIGHTING_OVERHAUL.md` were companion docs** in
   practice — one canonical lighting brief plus a focused refactor
   plan. The companion arrangement was healthy when both were
   actively churning; with R1+R2 of the refactor shipped via
   ENGINE_PACK_SPLIT R1, the remaining R3+R4 work was small
   enough to fold into the canonical doc as a new phase.
3. **Several shipped plans lacked an explicit status header.** A
   reader landing on the monorepo plan doc had to read the entire
   file to discover it was fully shipped historical reference,
   not active work.

## Option A vs Option B decision

The audit surfaced two reorg paths:

- **Option A (chosen):** Keep `docs/plans/` flat. Categorize only
  the root-level `docs/` files into `docs/process/` and
  `docs/audits/`. Merge LIGHTING_ENTITIES_REFACTOR into
  LIGHTING_OVERHAUL.
- **Option B (deferred):** Also categorize `docs/plans/` into
  subfolders (e.g. `docs/plans/active/`, `docs/plans/shipped/`).

**Why A:** `scripts/sync-plans.ts` walks `docs/plans/` with a
single-level `readdirSync` and mirrors each `.md` into the
Fumadocs `apps/docs/content/docs/plans/` tree. Subfoldering
`docs/plans/` would require making the sync recursive AND
re-organising the published navigation, both of which are
out-of-scope for a structural cleanup. Option A is the
conservative move that doesn't touch the live docs site.

If Option B becomes desirable later, the prerequisite is making
`sync-plans.ts` recursive and updating
`apps/docs/content/docs/plans/meta.json` to reflect the new tree.

## Tiebreaker rule

Where two docs being merged contained conflicting claims, **the
newer doc wins** (file mtime, or commit recency if mtime is
ambiguous). For the LIGHTING merge specifically, both source
files were last touched in the same commit (`3e7bcffe` on
2026-05-16). Inspection found no direct contradiction — the
LIGHTING_ENTITIES_REFACTOR doc's `§1 — Current state (post-R1/R2)`
described facts (R1+R2 shipped, R3+R4 remain) that LIGHTING_OVERHAUL
didn't claim either way, so the merge preserved them verbatim.
The companion-plan callout in LIGHTING_OVERHAUL was a pointer at
the now-merged doc; that callout was rewritten to point at the
new §13.
